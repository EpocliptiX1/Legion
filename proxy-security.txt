====================================================================
PROXY SECURITY — referer-locking + encrypted stream URLs
Written: 2026-08-17 (session continuing from vidscr.txt's reverse-engineering work)
====================================================================

WHY THIS EXISTS
----------------
Prompted by comparing ourselves to vidsrc.me/vidsrcme.ru: if someone were tasked
with "go get the raw stream" from our site vs. from vidsrc, they'd pick ours,
because our proxy endpoints put the real upstream CDN URL in plain text in the
query string, visible in any browser's network tab. vidsrc's own protection
(documented in vidscr.txt) is: ChaCha20-encrypted stream_urls, only decryptable
via a rotating WASM blob, plus short-lived signed tokens per host. We can't
(and don't need to) copy that exactly, but the same SHAPE of protection is
worth having: don't let the real URL travel through the browser in cleartext,
and make a copied link expire.

Two separate layers exist now. Layer 1 already existed before this session and
just needed to be found/verified. Layer 2 (AES token encryption) is new.


====================================================================
LAYER 1 — Referer/Origin locking (already existed, verified this session)
====================================================================

middleware.js is the ONLY thing browsers ever talk to (port 3000, HTTPS).
It reverse-proxies /api/* to the backend (port 4000, internal only).

requireSameOrigin() in middleware.js (~line 108):
  - Applied to ALL /api/* routes via `app.use('/api', requireSameOrigin);`
  - If the request has an Origin header, it must match our own Host (or
    ALLOWED_ORIGINS env list) or it's rejected with 403.
  - If it has no Origin but has a Referer, the Referer must start with our
    own origin, or it's rejected.
  - If it has NEITHER header, it's rejected outright (blocks plain curl/script
    hits with zero headers, which is the laziest kind of scraping).
  - skipLocalhost() bypasses ALL of this for requests originating from
    127.0.0.1/::1 — this is why every curl test done from the same machine
    during development "just works" without needing to fake headers. A real
    external request does NOT get this bypass.

Backend-side, independently:
  - server.js binds with `app.listen(PORT, 'localhost', ...)` — not reachable
    from the network at all, only from the same machine.
  - Every route also requires an `x-middleware-secret` header matching
    MIDDLEWARE_SECRET, which only middleware.js knows and injects when it
    forwards a request. Direct hits to :4000 get a flat 403 regardless of any
    other header.

KNOWN WEAKNESS (inherent to the technique, not a bug):
  Referer/Origin headers are attacker-controlled. Anyone willing to set a fake
  header defeats this layer entirely. It stops the laziest scraping (curl with
  no headers, or a script that never bothers) but not a determined one. That's
  exactly why Layer 2 exists — it protects the URL itself, not just who's
  allowed to ask for it.

  Also found (during the ngrok pentest tunnel): server.js had ITS OWN,
  separate, older origin check via app.use(cors({...})) - hardcoded to
  localhost:3000 by default, independent of and stricter than
  requireSameOrigin above. Since the backend is already unreachable except
  through that check (localhost-only bind + the secret-header guard below -
  only middleware.js can produce a request that gets this far), this second
  check added no real protection, just broke anything not literally
  localhost:3000 (the ngrok tunnel, and would've broken any real production
  domain too unless someone remembered to keep ALLOWED_ORIGINS in sync).
  FIXED: simplified to `cors({ origin: true, credentials: true })` - still
  sets proper CORS response headers, no longer redundantly re-rejects origin.

  Also found: MIDDLEWARE_SECRET had no .env override anywhere, so it was
  running on a hardcoded default value that sat directly in server.js's
  source — and the repo (EpocliptiX1/Legion) is public on GitHub, so that
  "secret" was public too. FIXED this session: both server.js and
  middleware.js now load/generate a shared random secret via
  Backend/secretStore.js -> Backend/middleware_secret.key (gitignored, same
  "generate once, persist, both processes read the same file" pattern as
  proxy_token.key below). Set MIDDLEWARE_SECRET as a real env var to override
  this if you ever want to manage it that way instead.

  Separately, and bigger, and explicitly deferred (user said to leave it):
  Backend/users.db and Backend/activity.db (real user emails, bcrypt hashes,
  watch history) are tracked in git with commit history, also public. Flagged
  to the user twice, confirmed both times to leave it alone — not touched.

LAYER 2 — AES-256-GCM encrypted proxy tokens (new this session)
====================================================================

THE PROBLEM THIS SOLVES
Even with Layer 1 fully working, /api/m3u8-proxy?url=https://real-cdn.com/...
puts the real CDN URL in plain text in the query string. Layer 1 only checks
WHO is allowed to call our endpoint — it does nothing to hide WHAT the
endpoint actually points at. Anyone using the site normally (a real browser,
real Referer, totally legitimate) can still open devtools, copy that URL out,
and hit the real CDN directly forever — completely bypassing our site, our
Referer check, everything, since the real CDN doesn't know or care about any
of that.

THE FIX
Pack {url, referer, userAgent, expiresAt} into one AES-256-GCM encrypted,
base64url-encoded token. The browser only ever sees this opaque token, never
the real URL. server.js decrypts it server-side right before making the real
request.

Location: Backend/server.js, right after the MIDDLEWARE_SECRET guard (~line 1319)

  PROXY_TOKEN_KEY_FILE = Backend/proxy_token.key
    - 32 random bytes, base64-encoded, generated ONCE on first run and
      persisted to disk (NOT regenerated per process/restart). If it were
      regenerated on every restart, every token already handed to a browser
      mid-episode would instantly stop decrypting — a page reload isn't
      supposed to kill your stream.
    - Added to .gitignore. This file IS a real secret — same failure mode as
      the MIDDLEWARE_SECRET issue above if it ever gets committed.

  PROXY_TOKEN_TTL_MS = 2 hours (was 6h - see PENTEST FINDINGS below)
    - A fresh token is minted every time an episode/title LOADS (not once per
      binge session) - it only has to outlive one title's active viewing, not
      a whole session watching many episodes back to back. 2h covers even a
      long movie plus a real pause.

  encryptProxyTarget({ url, referer, ua })
    -> JSON payload {u, r, a, e} -> AES-256-GCM encrypt with a random 12-byte
       IV -> Buffer.concat([iv, authTag, ciphertext]) -> base64url string.
       (base64url specifically because it has no +, /, or = characters that
       would need URL-encoding in a query string.)

  decryptProxyTarget(token)
    -> reverse of the above. Throws if:
       - the token doesn't decode/decrypt (GCM's auth tag catches ANY
         tampering — flip one character and decryption fails outright,
         doesn't just silently produce garbage)
       - payload.e (expiry) has passed
    Verified all three failure modes directly (see chat history): a correct
    round-trip, a tampered token, and an expired token all behave correctly.

  buildM3u8ProxyUrl(url, referer)   -> "/api/m3u8-proxy?token=<encrypted>"
  buildStreamProxyUrl(url, referer, ua) -> "/api/proxy-stream?token=<encrypted>"
    These are THE functions to use anywhere a proxy URL needs to be built,
    going forward. Don't hand-roll ?url=... again.

ENDPOINT CHANGES
  /api/m3u8-proxy and /api/proxy-stream both accepted EITHER a token or the
  legacy ?url=&ref= pair during this session's gradual migration. As of
  LAYER 3 below, the legacy fallback is retired - see that section.
  Both also had their internal manifest-rewriting logic (the part that turns
  nested #EXT-X-STREAM-INF / #EXT-X-MEDIA / segment lines inside a proxied
  .m3u8 into more proxy URLs, so hls.js keeps following everything through
  us) switched to emit tokens instead of raw ?url= too.

IMPORTANT: tokens are built AT RESPONSE TIME, not at cache-write time.
  episode_load_cache (SQLite, 24h TTL) still stores the RAW url internally —
  it has to, since a 6h token would go stale before a 24h cache entry does.
  Every route wraps the cached raw url in a FRESH buildM3u8ProxyUrl() call on
  every read, cache hit or not. If you ever add a new cached provider, follow
  this same pattern: cache raw, tokenize on the way out, never the reverse.

MIGRATION STATUS — who's actually using tokens right now
====================================================================

EVERY provider is now hardened. Full list:
  - KAA               — proxiedKaaUrl() helper (server.js ~8866), used for
                         both video sources AND subtitle URLs
  - NekoStream         — /api/anime-neko-log, cache-hit + fresh-resolve paths.
                         Covers its MegaPlay fallback path too (proxyRef
                         threaded through correctly for that case).
  - RU-MV (anime)      — /api/anime-new-log, both paths
  - MegaPlay           — /api/anime-megaplay-log
  - Kino (movie + TV)  — /api/movie-kino-log, /api/tv-kino-log
  - RU-Movie           — /api/movie-ru-log
  - RU-TV              — /api/tv-ru-log
  - MegaPlay/Neko subtitle TRACKS — tokenizeMegaplayTracks() helper
    (server.js ~1385), turns raw {file, label, kind, default} into the final
    {url, lang, default} shape server-side, same cache-raw/tokenize-on-read
    rule as the video streams. Frontend no longer touches .file at all in any
    of the 4 spots that used to build a proxy URL from it by hand.

  Frontend (js/moviePlayer.js): every provider's loader now uses data.stream/
  ex.stream DIRECTLY as the already-built proxy URL, and subtitle tracks are
  used as-is instead of mapped from a raw .file field. Several spots would
  have actively broken once the backend contract changed (double-wrapping a
  relative path as if it were an absolute url= target, or filtering on a
  .file field that no longer exists on a tokenized track) — caught and fixed
  as each provider was migrated.

NOT HARDENED: nothing. The legacy ?url=/&ref= fallback that used to exist for
anything not-yet-migrated has been fully retired (see LAYER 3) - both proxy
endpoints now REQUIRE a valid, session-bound token. Any new provider added in
the future must call buildM3u8ProxyUrl/buildStreamProxyUrl from day one, or
it simply won't work (no silent unhardened fallback path to fall into).

HOW TO MIGRATE ONE OF THE ABOVE (the repeatable recipe):
  1. Find the backend route that resolves the raw stream URL (grep for
     `stream:` in its res.json(...) call).
  2. Wherever it currently does `stream: rawUrl`, change it to
     `stream: buildM3u8ProxyUrl(rawUrl, refererIfAny)`.
  3. If that route caches its result (episodeLoadCacheGet/Set), make sure the
     CACHE still stores the raw url — only wrap it on the way OUT, in both the
     cache-hit branch and the fresh-resolve branch.
  4. Find the frontend loader for that provider in js/moviePlayer.js — it'll
     have a line like:
        const proxiedStreamUrl = `/api/m3u8-proxy?url=${encodeURIComponent(data.stream)}...`
     Delete that wrapping — just use `data.stream` directly, since it's
     already a full proxy URL now.
  5. `node --check` both files, restart the backend, reload the page, test
     actual playback for that provider before moving to the next one.


====================================================================
PENTEST FINDINGS — fresh-session security test, run by a separate Claude
instance (no source access, browser/network only via ngrok tunnel)
====================================================================

ROUND 1 — caught a real, self-inflicted regression (not a design flaw):
  Tested mid-migration, after the frontend had already stopped wrapping
  data.stream in /api/m3u8-proxy?url=... (assuming the backend always
  returns pre-tokenized URLs now) but BEFORE the backend had been restarted
  to actually start doing that. Result: raw upstream CDN URLs (JWT and all -
  vidsrcme's own token, decoded live: {iss:"my-auth", ip_cidr, exp - 4h
  window}) went straight to the browser, completely unwrapped. Worse than
  the pre-session baseline, purely because of restart-ordering, not a flaw
  in the token scheme itself. Fixed by restarting the backend - lesson:
  frontend/backend contract changes that swap "wrap it here" for "it's
  already wrapped" are NOT safe to deploy out of order.

ROUND 2 — post-restart, found the real design gap:
  Confirmed the raw upstream URL is never exposed anymore (good - the fix
  from round 1 held). But: captured a live /api/m3u8-proxy?token=... URL and
  replayed it with a plain fetch() - no cookies, spoofed Origin/Referer,
  completely detached from any site session. Still 200, still played.
  Tampering the token (flip a char, truncate, garbage) correctly 403'd,
  confirming it's genuinely signed/encrypted, not just obscured - so this
  ISN'T "anyone can mint a token for arbitrary content," it's "a valid,
  captured token is a fully self-contained bearer credential for its whole
  TTL, no session/origin binding at all."
  This was true by design (see LAYER 2 above - the whole point was letting a
  page reload/second tab keep working without re-resolving), but the TTL
  was set wrong: 6 hours, reasoned as "cover a full binge session," when a
  fresh token actually mints on every episode/title LOAD, not once per
  binge. That made the exposure window 72x longer than vidsrcme's own
  ~5-minute tokens (the thing this scheme was modeled after) for no real
  benefit. FIXED: PROXY_TOKEN_TTL_MS dropped to 2 hours (still safely covers
  one long movie + a pause, cuts the window 3x).

  Cross-title token reuse: not tested live, but structurally impossible -
  the target URL is INSIDE the encrypted payload ({u: url, ...}), not a
  separate lookup key. A token minted for one resource can only ever decrypt
  back to that exact resource.

SECONDARY FINDING — /api/kino-subtitle-vtt is an open server-side fetch
proxy for arbitrary external URLs (by design - it fetches whatever subtitle
host OpenSubtitles points at). Confirmed it DOES correctly block loopback/
link-local/private ranges and a DNS-rebinding attempt (127.0.0.1.nip.io), so
no real SSRF into internal infra. Residual risk is low: using the server as
a fetch relay to hide requester IP against third-party sites, and it always
labels responses text/vtt regardless of real content-type (minor content-
confusion smell, not fixed - not worth the complexity for the actual risk
level here).

RESOLVED (see LAYER 3 below): tokens now bind to a session cookie, closing
this gap - a captured token+URL is no longer replayable from a different
machine at all, not just "within 2h instead of 6h."


====================================================================
LAYER 3 — Session-bound tokens (new this session, 2026-08-17)
====================================================================

THE PROBLEM THIS SOLVES
Round 2 of the pentest (above) found that a captured /api/m3u8-proxy?token=...
URL was a fully self-contained bearer credential - replayable via plain
fetch(), no cookies, spoofed headers, completely detached from any browser
session, valid for the whole 2h TTL from anywhere. Shortening the TTL (already
done) reduces the exposure window but doesn't close it - this layer does.

THE FIX
Every visitor gets a session cookie (aniko_sid: 64 hex chars, HttpOnly,
Secure, SameSite=Lax, 24h lifetime - independent of the 2h token TTL, per
explicit design decision: token TTL governs how long a stream stays
resolvable, cookie lifetime governs how long a browser is recognized as the
same visitor, and conflating the two would force unnecessary cookie churn
mid-binge). Set automatically on first request if missing/malformed
(server.js, ~line 1340-1360, in a global middleware before any route runs).

Every encrypted proxy token now carries the minting visitor's session id
INSIDE the encrypted payload ({u, r, a, s: sessionId, e}), not as a separate
lookup key - so tampering with it is caught by the same GCM auth tag as
everything else in the token.

/api/m3u8-proxy and /api/proxy-stream now call verifyProxySession(req,
decoded) right after decrypting: if the token's embedded sessionId doesn't
exactly match the CALLER's own aniko_sid cookie, hard-reject with 403 ("This
link does not belong to your session"), distinguished from the generic
"Invalid or expired proxy token" message for a malformed/expired token. Since
aniko_sid is HttpOnly, it's invisible to JS (can't be read/exfiltrated by
injected script) and doesn't travel with a manually-copied URL (cookies
aren't part of a URL) - so a captured link is useless without also somehow
obtaining that exact browser's session cookie.

LEGACY FALLBACK RETIRED (per explicit instruction: "Enforce session-token
binding across all proxy routes without exemption... we are not 'out in the
world' yet, so we need to take this chance to patch up old code"):
  Both /api/m3u8-proxy and /api/proxy-stream now REQUIRE ?token=... - the old
  ?url=&ref=&ua= plaintext fallback (kept in LAYER 2 as a gradual-migration
  aid) is gone entirely. Every provider was already migrated to tokens, so
  this closes the door rather than leaving a permanently-unauthenticated
  escape hatch lying around.

buildM3u8ProxyUrl(url, referer, sessionId) and buildStreamProxyUrl(url,
referer, ua, sessionId) both take sessionId as a real (no-default) parameter
now - every call site across all 7 provider routes plus tokenizeMegaplayTracks
threads req.sessionId through.

A REAL BUG CAUGHT WHILE BUILDING THIS (not user-reported):
  KAA's caching was structured differently from every other already-migrated
  provider - resolveKickAssAnimeSources() baked the final tokenized
  proxiedUrl into `sources`/`subtitles` BEFORE the result was written to the
  24h episode_load_cache. Under Layer 2 alone this was harmless (tokens just
  went stale after 2h and got silently ignored/errored). But it would have
  been a real bug under Layer 3: a cached KAA entry's tokens would be
  permanently bound to whichever visitor's session happened to trigger the
  cache write, breaking playback for every OTHER visitor who hit that cache
  entry afterward. FIXED by restructuring to the same cache-raw/tokenize-on-
  read pattern already used everywhere else: resolveKickAssAnimeSources() now
  returns raw sources/subtitles/headers; a new tokenizeKaaResult(rawResult,
  sessionId) builds the actual proxy URLs at RESPONSE time, called from both
  the cache-hit and fresh-resolve branches of /api/anime-kaa-servers, plus
  /api/animepahe/:malId/:ep/:type. Also had to fix a second cache-WRITE site
  (/api/anime-kaa-availability's checkOne) that was still writing the old
  bare-array cache shape, which would have broken the new read-side
  destructuring if left alone.

FRONTEND: no changes needed. js/moviePlayer.js's fetch() calls to /api/*
already default to same-origin credentials (nothing sets `credentials:
'omit'` anywhere in the file), and aniko_sid is a normal same-origin cookie -
the browser attaches it automatically to every request to our own domain,
same as any <video>/hls.js request for a proxied stream URL. Verified by
grepping the whole file for "credentials" (no matches).

ROUND 3 — full compromise via static file exposure (2026-08-17/18,
separate pentest session, no source access, browser+curl via ngrok
then direct localhost:3000 once ngrok hit its bandwidth cap)
====================================================================

HOW THIS ROUND STARTED
Round 2 (above) had already closed the session-binding gap. This round set
out to re-verify that fix plus sweep for anything unrelated. The very first
thing tried — `GET /Backend/users.db` — returned HTTP 200 with the raw
SQLite file. That one request unraveled into the worst finding of the whole
engagement, so the play-by-play matters here, not just the conclusion.

THE ROOT CAUSE
Whatever was serving static files (almost certainly `express.static()`
mounted on the repo root, or on `Backend/` itself, instead of a dedicated
`public/`-only directory) had zero allowlist/denylist on file type or
location. A plain `GET` to a guessed path served ANYTHING under that mount
point verbatim: source code, databases, secret key files, debug logs — all
of it, same as if you'd `cat`ed the file locally.

WHAT WAS ACTUALLY DOWNLOADABLE (all confirmed HTTP 200, full body):
  /Backend/server.js              675KB — the ENTIRE backend source, i.e.
                                   everything documented in this file
  /Backend/proxy_token.key        the AES-256-GCM key from LAYER 2 above,
                                   in plaintext, 44 bytes, base64
  /Backend/middleware_secret.key  the MIDDLEWARE_SECRET from LAYER 1 above,
                                   plaintext, 64 hex chars
  /Backend/users.db               7.9MB SQLite dump, 107 real users
  /Backend/backend/users.json     34KB, same 107 users as JSON: username,
                                   userEmail, userTier, userPassword
                                   (bcrypt $2b$10$..., 60 chars — hashed,
                                   not plaintext, that part was fine), plus
                                   an `admin` account in the dump
  /Backend/activity.db, /Backend/animeCache.db, /Backend/poster_cache.db,
  /datasets/movies.db             assorted other DB dumps
  /Backend/kaa-debug-log.txt, /Backend/episode-logs.txt,
  /Backend/tmdb_search_log.txt, etc.   assorted logs

WHY THE KEY LEAK IS CATASTROPHIC (not just "one more leaked file")
Every other finding in this document assumes the AES key and the middleware
secret are secret. Once they're not, none of the LAYER 1/2/3 protections
above are actually enforcing anything — they're just code that LOOKS like
protection to someone reading it, not protection that holds up against
someone who has the key. Proved this three separate ways, each one a
complete, working bypass built entirely offline from the leaked key, with
NO interaction with the real resolver/session flow at all:

  1. DECRYPT any captured token without ever touching a session.
     Grabbed a live /api/proxy-stream?token=... URL, wrote ~10 lines of
     Node reimplementing decryptProxyTarget() with the leaked key:

       const raw = Buffer.from(token, 'base64url');
       const iv = raw.subarray(0,12), authTag = raw.subarray(12,28),
             ciphertext = raw.subarray(28);
       const decipher = crypto.createDecipheriv('aes-256-gcm', LEAKED_KEY, iv);
       decipher.setAuthTag(authTag);
       JSON.parse(Buffer.concat([decipher.update(ciphertext), decipher.final()]))

     -> {"u":"https://bl.krussdomi.com/playlist/.../master.m3u8", "r":"...",
         "a":"...", "s":"<session id>", "e":<expiry ms>}
     The exact same {u,r,a,s,e} shape documented in LAYER 2/3 above,
     recovered with zero access to the app itself.

  2. FORGE a brand new, fully valid token from scratch.
     Same script, run in reverse (encryptProxyTarget logic instead of
     decrypt), with a sessionId of `'a'.repeat(64)` — a session that was
     NEVER issued by the real server, just typed in. Sent it as
     `Cookie: aniko_sid=aaaa...a` (64 chars, matches the format check) +
     the forged token as `?token=...`. Server returned 200 with a real,
     playable HLS manifest. This is the part that actually breaks LAYER 3:
     verifyProxySession() correctly checks decoded.sessionId === req.sessionId
     — but with the key known, an attacker controls BOTH sides of that
     comparison simultaneously (bakes whatever sessionId they want into the
     token, then sends a cookie with that same string), so the check passes
     every time regardless of what it's comparing. The check's logic was
     never wrong; the secret it depends on was just public.

  3. BYPASS the internal-backend gate on :4000 entirely.
     The leaked middleware_secret.key value, sent as `x-middleware-secret`,
     turned every `403 Forbidden: direct access to backend is not allowed`
     from LAYER 1 into a normal (allowed-through) response.

  Also relevant: the session cookie itself was, at the time, validated by
  format only (`/^[a-f0-9]{64}$/`) with no server-side session store behind
  it — so step 2 above didn't even require defeating a signature, just
  matching a regex. (This got hardened as part of the fix — see below.)

THE FIX (confirmed, re-tested from scratch afterward)
  - Whatever was over-broadly serving `Backend/` was locked down — every
    path under `/Backend/*` now returns a flat 404, not just the specific
    files found. Re-tested ~20 paths across all the categories above,
    all 404.
  - Both `proxy_token.key` and `middleware_secret.key` were ROTATED, not
    just hidden. Confirmed by trying to decrypt a freshly-minted live token
    with the old leaked key value: `Unsupported state or unable to
    authenticate data` (GCM auth tag rejects it outright — this is what
    "rotated, not just moved" looks like from outside: the old key
    literally stops working, instantly, for every token minted after the
    rotation). Same for the middleware secret: old value -> back to 403 on
    :4000.
  - The session cookie was upgraded from a bare 64-hex-char value to a
    signed `<id>.<signature>` pair. Tested: a well-formed-but-wrong
    signature gets fully discarded (server mints and sets a brand new
    legitimate session instead of trusting the malformed one) rather than
    accepted on format alone.

A SECOND, SMALLER BUG FOUND WHILE RE-VERIFYING THE ABOVE:
  `POST /users` let an authenticated user change their OWN account's
  `userEmail` field with no current-password confirmation — meaning a
  stolen/leaked bearer token (e.g. via XSS, see ROUND 5) could be used to
  silently take over an account by first swapping the recovery email before
  the real owner noticed anything.
  FIX: confirmed `POST /users` now requires `currentPassword` whenever the
  request body includes an email change; wrong/missing password -> rejected
  with `"Current password required to change email"`. Verified live against
  a fresh test account: no-password attempt rejected, correct-password
  attempt succeeded, tier field on the same route left alone since the user
  scoped that piece out as a non-issue (see ROUND 4).


====================================================================
ROUND 4 — different attack surface: SSRF audit, scraped-content XSS
audit, and the (explicitly deprioritized) tier/paywall gap
====================================================================

METHOD NOTE: this round deliberately avoided repeating the ROUND 3
playbook (key forgery) and instead picked two structurally different
bug classes to hunt for, since finding the SAME class of bug three times
in a row tells you less than checking two you haven't looked at yet.

SSRF AUDIT — clean, no fix needed
  Every server-side scraper that fetches a third-party URL based on
  user-supplied input was traced by hand: TMDB proxy (`/api/tmdb-proxy/*`),
  Jikan (`jikanGet()`), Anikoto comment/reply fetchers, the Kinogo comment
  importer (`resolveKinogoMoviePageForComments`/`fetchKinogoComments`), and
  OpenSubtitles (`searchKinoSubtitles`). In every single case, the request
  URL is built as `FIXED_HOST_STRING + userInput`, where userInput only
  ever lands in the PATH or QUERY, never the authority/host portion. That
  means there's no `new URL(userInput, base)`-style construction anywhere
  that a crafted input could hijack into pointing at a different host
  (internal service, cloud metadata endpoint, etc.) — the pattern that
  usually causes SSRF just doesn't exist in this codebase's scrapers.
  Specifically checked for (and didn't find): protocol-relative host
  overrides (`//evil.com`), path traversal escaping the hardcoded prefix,
  and unbounded `axios.get(fullUserSuppliedUrl)` calls anywhere.

STORED XSS VIA SCRAPED THIRD-PARTY CONTENT — clean, no fix needed
  The theory: your scrapers pull `username`/`text` from real posts on
  kinogo.mu/anikoto.cz and store+display them on your own pages. If someone
  posts a payload on THEIR site and it gets imported verbatim, it executes
  in YOUR users' browsers once rendered here — a stored XSS where the
  "attacker input" never even touches your own API. Traced the actual
  render path (`renderOneComment()` -> `escapeHtml()` on both username and
  comment text, BEFORE any markdown-style transforms are applied) and
  confirmed it's escaped correctly, consistently, for every comment source
  (user-authored, kinogo-imported, anikoto-imported alike). The one spot
  that WASN'T doing this consistently turned out to be a different bug
  entirely — see ROUND 5's profile-picture XSS below, which was found
  while specifically re-checking this exact rendering pipeline for gaps.

TIER/PAYWALL SERVER-SIDE ENFORCEMENT — found, reported, explicitly
DEPRECATED per user instruction ("ignore it, will be removed")
  `POST /users/me/increment-view` increments a counter unconditionally and
  never blocks anything; nothing anywhere in the streaming resolve chain
  (`/api/anime-kaa-servers`, `/api/m3u8-proxy`, `/api/proxy-stream`, or any
  of the seven other provider routes) checks `userTier` or `viewCount`
  before serving a stream. A completely fresh, never-registered anonymous
  guest session gets the exact same working proxied stream token as a
  paying account. Left as-is per explicit user direction — noting it here
  only so it isn't rediscovered from scratch next time someone reads this
  file. If this ever needs picking back up: the check belongs in whichever
  function is common to all provider routes right before token minting, not
  bolted onto each of the eight individually.

ROUND 5 — comment/account feature audit + a real stored XSS

COMMENT DELETE IDOR — clean, no fix needed
  Posted a comment as account D, attempted `DELETE /movie-comments/:id` and
  `DELETE /anime-comments/:id` as unrelated account E. Both correctly
  403 `"You do not own this comment"`. Owner-delete still works.

MERGE-ACCOUNT PASSWORD CHECK + BRUTE FORCE — clean, no fix needed
  `POST /users/merge-account` takes {sourceEmail, sourcePassword} under the
  CALLER's own bearer token, and is supposed to verify sourcePassword
  actually authenticates sourceEmail before merging (and deleting!) that
  account into the caller's. Wrong password -> 401 `"Incorrect password for
  that account"`. Correct password -> succeeds and genuinely merges/deletes
  the source account (confirmed with two disposable test accounts, not real
  user data). Hammered it with 15 wrong-password attempts against a real
  target account: attempts 1-6 get normal 401s, attempt 7 onward clamps to
  429 and stays there — a real, working rate limiter (`strictLimiter` in
  the source), not just a documented intention.

CSRF ON THE STREAM ENDPOINTS — found, then fixed same session
  Mutation endpoints (comments, merge-account, `/users`) authenticate via
  `Authorization: Bearer <jwt>` (localStorage, not a cookie) — a cross-site
  page literally cannot attach that header automatically, so CSRF isn't a
  meaningful concern there by construction, no token needed.
  BUT `/api/proxy-stream` and `/api/m3u8-proxy` authenticate via the
  `aniko_sid` cookie, and originally accepted requests carrying a
  completely foreign `Origin`/`Referer` (or none at all) just fine — the
  Referer/Origin check documented in LAYER 1 wasn't actually being enforced
  on these two specific routes. Didn't cross a session boundary in practice
  (the LAYER 3 session-binding check is what was actually doing the real
  work, and that held throughout), but it was thinner defense-in-depth than
  documented, and combined with `Access-Control-Allow-Origin: *` on these
  responses meant any third-party site could freely embed a stream URL
  (only ever usable with the embedding VIEWER's own valid session, so not a
  privilege escalation on its own — still worth closing, belt-and-suspenders).
  FIX: confirmed both proxy endpoints now reject foreign-origin requests
  (re-tested live with a spoofed external `Origin`/`Referer` — properly
  blocked), and the three hardcoded `Access-Control-Allow-Origin: *`
  responses were tightened to reflect the validated caller origin instead.

STORED XSS: profile picture -> comment avatar (the real one this round)
  Two independent small bugs that chain into one working exploit:

  1. `POST /users/profile-picture` validated only the PREFIX of the
     `profilePic` data URI (`data:image/png;base64,`) — never checked that
     everything after the comma was actually valid, size-bounded base64
     image data. Sent:
       data:image/png;base64,iVBOR...==');}</style><script>alert(document.cookie)</script><style>a{background:url('
     and the server stored it verbatim: `{"success":true}`.

  2. `commentAvatarHTML()` (js/movieLoading.js) rendered `profilePic`
     completely UNescaped, directly into
       <div class="comment-avatar" style="background-image:url('${profilePic}')"></div>
     — the one rendering spot in the whole comment-avatar/username/text
     pipeline that didn't route through `escapeHtml()` like everything else
     documented as clean in ROUND 4's XSS audit above. (This is exactly why
     that audit is worth re-running periodically rather than treated as a
     permanent clean bill of health — a single new render call anywhere in
     the codebase can reopen the class of bug an earlier audit closed.)

  Proved the FULL chain end-to-end, not just the two halves in isolation:
  set the malicious profilePic on account D, had D post a real comment,
  then fetched `GET /movie-comments?movieId=...` with NO AUTHENTICATION AT
  ALL and got the poisoned `profile_pic` field back unmodified. Any visitor
  loading that comment section gets the script executed in their own
  browser — and since the JWT (`authToken`) lives in `localStorage`, not an
  HttpOnly cookie, `localStorage.getItem('authToken')` inside that injected
  script is a direct path to stealing another logged-in user's session and
  fully impersonating them. This was never just a cosmetic/defacement bug.

  FIX (confirmed):
  - Server now strictly validates the FULL base64 body (decodes it, checks
    it's real bounded PNG/JPEG/GIF/WEBP image data, magic bytes and all)
    and rebuilds the stored value from the decoded bytes rather than
    trusting the client-supplied string verbatim.
  - `commentAvatarHTML()` now runs `profilePic` through the same
    `escapeHtml()` used everywhere else before interpolating it — so even
    if server-side validation ever regresses again later, this specific
    sink doesn't reopen on its own.

ROUND 6 — remaining checklist items, plus port :4000's actual surface
====================================================================

PASSWORD STRENGTH POLICY — found, explicitly left as-is per user
  `userPassword: "1"` and `"a"` both accepted at registration; only a
  fully empty password is rejected. Given ROUND 3 showed the bcrypt hash
  DB has leaked once already, single-character passwords are effectively
  instant to crack offline regardless of hash cost factor. Flagged, user's
  call: "if someone uses 'a' as a pass, their fault" — noted here as a
  deliberate product decision, not an oversight, so it isn't miscategorized
  as unaddressed next time this file gets read.

LOGIN RATE LIMITING on /users/auth — confirmed real, working
  16ish wrong-password attempts get normal 401s, then it clamps to 429 and
  stays there. Real and working, just a looser threshold than
  merge-account's 6-attempt limiter. Given the password-policy decision
  above, this is the ONLY thing standing between a weak password and an
  online guessing attack (bcrypt cost + this limiter, no length/complexity
  requirement) — worth keeping in mind if that product decision ever gets
  revisited.

PORT :4000'S ACTUAL SURFACE — mapped, with the user's cooperation handing
over the live MIDDLEWARE_SECRET value for a scoped, authorized look
  Confirmed :4000 is NOT a separate/hidden/expanded API — it's the literal
  same Express app and route set as :3000 (identical results from
  `/api/tmdb/search?q=test` hit on both ports). Probed a dozen likely
  internal-only paths (`/admin`, `/debug`, `/metrics`, `/internal/*`) —
  all plain "no route matched" 404s, no evidence of hidden admin/debug
  functionality living behind the secret gate.
  Also confirmed :4000 is bound to `[::1]:4000` (IPv6 loopback) only, per
  `netstat` — not reachable from outside this machine under any
  circumstance, regardless of who has the secret. This matters a lot for
  severity: the one real bug found here (below) requires BOTH local machine
  access AND the secret to exploit at all.

  BUG FOUND: rate-limit bucket splitting via loopback address.
  Requests to :3000 arrive as `127.0.0.1` (IPv4); requests to :4000 arrive
  as `::1` (IPv6) — two different keys to an IP-keyed rate limiter, so each
  address gets its OWN independent quota. Confirmed: burned :3000's
  registration-endpoint quota to 429, then immediately got 200s via :4000
  for the identical action — a fresh bucket, not a shared one. This lets
  someone double their effective attempt budget on any rate-limited
  endpoint by working both addresses in parallel, PROVIDED they already
  have local access to the machine and the middleware secret (neither of
  which an external attacker has, per the loopback-only binding above).
  FIX (confirmed): re-ran the identical test — burned :3000's quota, then
  immediately hit :4000 for the same action — and :4000 now inherits the
  already-exhausted state instantly (429 right away, no fresh bucket).
  Whatever key the limiter uses is now normalized/shared across both
  listeners instead of keyed on the raw connecting address.

WATCH2GETHER SESSION OWNERSHIP — clean, no fix needed (nothing reproduced)
  Tested with two independent accounts against a real hosted-public
  session: reading another session's state without joining (403 "Not part
  of this session"), ending a session you don't host (403 "Not the host of
  this session"), granting yourself control (400 "Invalid request"),
  kicking the actual host as a non-host participant (403 "Not the host of
  this session"), and probing 8 adjacent/lower numeric session IDs against
  `join-public` to check for an existence-leak or private-session-guessing
  path (all uniform 404 `"Public session not found"` — doesn't even
  distinguish "exists but not public" from "doesn't exist", which is the
  right behavior to avoid enumeration). Every ownership check held up.

GUEST ACCOUNT / MERGE-GUEST ABUSE — clean, no fix needed
  Guest UIDs (`g_` + 24 hex chars) are generated client-side via
  `crypto.getRandomValues()` — 96 bits of entropy, not guessable or
  practically enumerable, so `POST /users/merge-guest` can't realistically
  be abused by guessing someone else's guest ID.

SESSION COOKIE SIGNATURE TIMING ATTACK — attempted, genuinely inconclusive
  Tried to detect a non-constant-time signature comparison by timing two
  batches of 20 requests each (wrong-from-byte-one vs. wrong-throughout-at-
  a-different-value) against the same endpoint. Result: 9.16ms vs 9.41ms
  average, both well inside the ~3ms request-to-request jitter present in
  EACH batch individually — no usable signal, but that's the expected
  outcome of this measurement method, not evidence either way. A real
  timing side-channel in an HMAC comparison lives at the nanosecond-to-low-
  microsecond scale; the noise floor of "spawn a curl process, do a TCP+TLS
  handshake, hit a Node event loop" is roughly 1000x too coarse to see
  through. This specific question (is the comparison constant-time?) can
  only be answered by reading the comparison code directly or running a
  proper in-process microbenchmark — not from outside over HTTP. Left open,
  flagged as "unknown," not "safe."
